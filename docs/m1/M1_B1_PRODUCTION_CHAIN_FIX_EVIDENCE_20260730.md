## 2. Root Cause

The previous B1F implementation correctly created and validated
`m1.confirmed-input.v1`, but the production mount stopped at a default no-op
callback:

```text
App.jsx
  -> M1ConfirmedInputPanel
  -> createM1ConfirmedInput
  -> default onConfirmed no-op
```

The earlier real-browser evidence compensated with a repository-external Vite
harness. Its counter could reach one, but that wiring was not present in the
production App. The committed UI tests used `renderToStaticMarkup`, so they
could not expose the disconnect.

The correction connects the existing browser confirmation flow to a
server-side Core input boundary. This is necessary because the frozen
`m1DecisionCore.js` uses Node's canonical SHA-256 implementation and must not
be copied or reimplemented in browser code.

## 4. Production App-to-Core Chain

The current production chain is:

```text
natural-language question
  -> App.jsx / AskPowerInsightTab
  -> M1ConfirmedInputPanel.startUnderstanding
  -> requestM1InputResolution
  -> POST /api/m1-input-understanding
  -> public m1_input_context or bounded unavailable result
  -> createM1InputResolutionFromUnderstandingResult
  -> READY_FOR_CONFIRMATION or FALLBACK_CONFIRMATION_REQUIRED
  -> same M1ConfirmedInputPanel
  -> createM1ConfirmedInput
  -> validateM1ConfirmedInput
  -> App.jsx.handleM1Confirmed
  -> submitM1ConfirmedInputToDecisionCore
  -> POST /api/m1-input-understanding with action=m1_confirmed_input
  -> handleM1ConfirmedInputSubmission
  -> existing buildM1DecisionResolutionRequest
  -> existing assertM1ConfirmedInputGate
  -> existing canonical SHA-256 facts/status binding
```

`App.jsx` explicitly renders:

```jsx
<M1ConfirmedInputPanel
  question={question}
  onConfirmed={handleM1Confirmed}
/>
```

The confirmation action enters the existing production Core function
`buildM1DecisionResolutionRequest`. It does not create a parallel Core,
duplicate SHA implementation, or test-only decision algorithm.

The Core input request is constructed and validated locally. Decision
Resolution Provider execution is not invoked in this gate.

## 5. Exactly-Once Design

Exactly-once is enforced at two production boundaries:

1. `M1ConfirmedInputPanel`
   - claims a synchronous `confirmationSubmittedRef` before building the
     confirmed input or awaiting network work;
   - a second click in the same event turn returns immediately;
   - the confirmation button becomes disabled;
   - no `useEffect` watches confirmed state;
   - editing explicitly starts a new confirmation attempt.
2. `App.jsx`
   - stores the Promise for each confirmed-input object in a `WeakMap`;
   - a duplicate callback for the same confirmation event returns the same
     Promise rather than issuing a second request.

React Strict Mode remains enabled in `src/main.jsx`. Strict Mode rerendering
does not execute the event callback. Browser testing dispatched one double
click, then an additional rerender-triggering resize event:

```text
preConfirmationCoreCalls = 0
postConfirmationCoreCalls = 1
doubleClickSubmissionCalls = 1
strictMode = true
```

No automatic Core retry exists.
